# Prometheus and Grafana monitoring

Issue: #42. Source: `.changes/proposals/observability.md`, section 1.

## Problem Statement

The cluster has no metrics. An operator cannot see whether pods, nodes, the eleven services, Kafka, Redis, Postgres or MongoDB are healthy without running `kubectl` by hand.

## Solution

Deploy Prometheus and Grafana as plain manifests under `k8s/infra/monitoring/`, with the exporters and per-service `/metrics` endpoints they need, plus three provisioned dashboards (cluster, services, infra).

Open question from the issue, settled: **plain manifests, not `kube-prometheus-stack`.** Reasons: every other component in `k8s/infra/` is a hand-written manifest, so this matches the repo; the chart brings the Prometheus Operator, CRDs and dozens of objects for a single-node local cluster; rendering a chart through kustomize needs `--enable-helm` and a helm binary the project does not otherwise use; and the course goal is to understand the pieces. Ceiling: no ServiceMonitor CRDs and no bundled alert rules; revisit if Alertmanager is added later.

## User Stories

1. As an operator, I want Prometheus to scrape every service and exporter, so that one page (`/targets`) tells me what is up.
2. As an operator, I want node and pod metrics (`node-exporter`, `kube-state-metrics`), so that I can see capacity and restarts.
3. As an operator, I want each Java service to expose `/actuator/prometheus`, and each Go and Python service `/metrics`, so that request rate, latency and runtime health are visible per service.
4. As an operator, I want Kafka, Redis, Postgres and MongoDB exporters, so that infra health is visible.
5. As an operator, I want Grafana to start with the Prometheus data source and three dashboards already provisioned, so that nothing is configured by hand after `kubectl apply`.

## Implementation Decisions

- **Layout:** all new infra in `k8s/infra/monitoring/` with its own `kustomization.yaml`. Apply with `kubectl apply -k k8s/infra/monitoring`. The existing `kubectl apply -f k8s/infra/` is not recursive, so it ignores the folder; no shared kustomization or existing infra file is edited. One README line documents the command.
- **Namespace** `raas`, like the rest of `k8s/infra/`.
- **Prometheus** (`prom/prometheus`, pinned): Deployment, ClusterIP Service `prometheus:9090`, config from a ConfigMap generated by kustomize from `prometheus.yml`, storage `emptyDir` (`ponytail:` metrics are lost on restart; swap to a PVC if history matters). 15s scrape interval.
- **Discovery:** static targets by Service DNS (`<name>-service:80`, exporters by their own Service). Single replica per service, so static is exact, needs no RBAC for Prometheus and needs no edits to app manifests. Ceiling: scaling a service to N replicas scrapes only one per Service; move to `kubernetes_sd` pod discovery then.
- **kube-state-metrics:** Deployment + ServiceAccount + ClusterRole/Binding (read-only list/watch), Service `:8080`.
- **node-exporter:** DaemonSet, Service `:9100`, mounts host `/proc`, `/sys`, `/` read-only, `hostPID` and `hostNetwork` off (mounts only), so it reports the Docker Desktop VM.
- **Exporters:** `kafka-exporter` (`--kafka.server=kafka:9092`), `redis-exporter` (`REDIS_ADDR=redis://redis:6379`), `postgres-exporter` (DSN with the existing `raas_user` credentials against `raas_db`), `mongodb-exporter` (existing `raas_user` credentials, `--compatible-mode`). Credentials are inline in env, matching how `postgres.yaml` and `mongodb.yaml` already carry them.
- **Grafana** (`grafana/grafana`, pinned): Deployment, ClusterIP Service `grafana:3000`, provisioning ConfigMaps for the Prometheus data source and a dashboard provider, dashboards as JSON files in `dashboards/` turned into a ConfigMap by kustomize. Admin credentials from a Secret (`grafana-admin`, default `admin`/`admin` for local use). No ingress, no NodePort: access by `kubectl -n raas port-forward svc/grafana 3000` (avoids NodePort clashes with parallel work).
- **Dashboards (hand-written, small):** *Cluster* (node CPU/memory/disk, pod restarts, pods by phase), *Services* (up per service, request rate, p95 latency, 5xx rate, JVM heap for Java), *Infra* (Kafka consumer lag and topics, Redis memory/clients/ops, Postgres connections/transactions, MongoDB connections/ops).
- **Java** (`payment`, `review`, `favorites`): add `spring-boot-starter-actuator` and `micrometer-registry-prometheus`; in `application.yaml` expose only `prometheus` and `health` (`management.endpoints.web.exposure.include`). The services have no Spring Security, so the endpoint is open inside the cluster only; the gateway has no route to it.
- **Go** (`listing`, `media`, `booking`, all Echo): add `github.com/labstack/echo-contrib/echoprometheus`; `e.Use(echoprometheus.NewMiddleware("<service>"))` and `e.GET("/metrics", echoprometheus.NewHandler())`. The gateway does not route `/metrics`.
- **Python** (`user`, `notification`, `analytics`, all FastAPI): add `prometheus-fastapi-instrumentator` pinned to a version compatible with `fastapi==0.104.1`; `Instrumentator().instrument(app).expose(app)` after `app` is created.
- **Gateway and UI** are not instrumented (nginx; out of scope). Gateway is not a scrape target.

## Testing Decisions

Levels:

- **Unit / integration (services):** one test per stack proving the endpoint answers and carries a metric: Go `httptest` against the Echo app wiring (`GET /metrics` returns 200 and contains the service's request metric after one request); Java `@SpringBootTest` is heavy (DB, Kafka), so use the existing test setup only if it already boots a context, otherwise assert `management.endpoints.web.exposure.include` via a small properties test; Python FastAPI `TestClient` `GET /metrics` returns 200. Existing seams only; no new interfaces. Where a service's `main` builds the router inline, extract nothing: the test builds an Echo with the same two lines. (Tests prove the library contract, the deployment check proves the wiring.)
- **Manifests:** `kubectl kustomize k8s/infra/monitoring` renders cleanly; `kubectl apply --dry-run=server -k k8s/infra/monitoring` passes.
- **Deployment (local cluster):** all monitoring pods Ready; Prometheus `/api/v1/targets` shows every target `up`; Grafana API lists the data source and three dashboards; a query returns data (`up`, `kube_pod_info`, `node_cpu_seconds_total`).
- **Manual (human):** open the three dashboards in Grafana and confirm the panels show data and look right.

The local cluster must be running for the deployment and manual levels. If it is not, those levels are reported as not verified.

## Out of Scope

- Loki and log panels (Loki issue), MinIO (separate issue), Alertmanager and alert rules, tracing.
- Persistent storage for Prometheus and Grafana, ingress, TLS, auth beyond the admin secret.
- Instrumenting the nginx gateway and UI.
- Business-level custom metrics in services.
- CI changes (images are public upstream images; service CI already runs tests).
