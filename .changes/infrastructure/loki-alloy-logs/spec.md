# Loki and Grafana Alloy for central logs

Issue: #43. Source: `.changes/proposals/observability.md`, section 2. Depends on #42 (Grafana) and #41 (MinIO), both merged.

## Problem Statement

Logs live in each pod. To see why something failed, an operator runs `kubectl logs` pod by pod, and the logs are gone when the pod is replaced.

## Solution

Deploy Loki (monolithic, chunks and index in MinIO) and Grafana Alloy (DaemonSet) as plain manifests under `k8s/infra/logging/`. Alloy ships logs of all pods in namespace `raas` to Loki. Grafana gets Loki as a data source and one provisioned "Logs" dashboard.

Collector choice from the issue, settled: **Grafana Alloy**, not Promtail (maintenance mode). Fallback to Promtail only if the Alloy config proves too heavy to get working.

## User Stories

1. As an operator, I want logs of every `raas` pod in one place, so that I do not run `kubectl logs` per pod.
2. As an operator, I want to filter logs by app and pod in Grafana, so that I can follow one service.
3. As an operator, I want to see log volume and error-line rate per app, so that I notice a misbehaving service.
4. As an operator, I want logs to survive a pod restart, so that I can read what a crashed pod said.
5. As an operator, I want Loki to store its chunks in MinIO, so that log storage uses the object store the cluster already has.
6. As an operator, I want Grafana to start with the Loki data source and the Logs dashboard already provisioned, so that nothing is configured by hand after `kubectl apply`.

## Implementation Decisions

- **Layout:** new `k8s/infra/logging/` with its own `kustomization.yaml`, applied with `kubectl apply -k k8s/infra/logging`. `kubectl apply -f k8s/infra/` is not recursive, so it ignores the folder. Generated ConfigMaps set `namespace: raas` per entry, as `monitoring/` does. One README line documents the command right after the monitoring one; logging needs MinIO from the base infra apply.
- **Namespace** `raas`, like the rest of `k8s/infra/`.
- **Loki** (`grafana/loki:3.5.0`): single Deployment, `-target=all -config.expand-env=true`, one replica, `strategy: Recreate`, ClusterIP Service `loki:3100`, readiness probe `/ready`. Config from a ConfigMap generated by kustomize from `loki.yaml`. Monolithic keys that must be set or Loki fails on start: `auth_enabled: false`, `common.ring.kvstore.store: inmemory`, `common.replication_factor: 1`, `common.instance_addr: 127.0.0.1`, `common.path_prefix` and the compactor `working_directory` on an `emptyDir`. Schema v13: `store: tsdb`, `object_store: s3`, daily index period, `from` date in the past. Chunk flush: `chunk_idle_period: 1m`, `max_chunk_age: 5m`, so busy streams reach MinIO within minutes. Ingestion limits stay at defaults. `ponytail:` WAL and unshipped index live on the `emptyDir`; a Loki pod replacement loses them, and chunks flushed but not yet indexed (up to about 15m of tsdb upload lag) can become unqueryable. Use a PVC if that matters.
- **MinIO wiring:** `common.storage.s3` with `endpoint: minio:9000`, `s3forcepathstyle: true`, `insecure: true`, `region: us-east-1`, `bucketnames: raas-loki`. Credentials come from the existing `minio-credentials` Secret, mapped to env vars `MINIO_ROOT_USER` and `MINIO_ROOT_PASSWORD` and referenced as `${MINIO_ROOT_USER}` and `${MINIO_ROOT_PASSWORD}` in the config (the config contains no other `$`). The Secret is not copied. Known deviation: Loki uses the MinIO root credentials, not a scoped user; acceptable for dev, like the other inline credentials. Loki does not create buckets, so an `initContainer` (`cgr.dev/chainguard/minio-client`, pinned by digest) runs `mc mb --ignore-existing minio/raas-loki` in exec form. The image is distroless (no shell), so it authenticates through env `MC_HOST_minio=http://$(MINIO_ROOT_USER):$(MINIO_ROOT_PASSWORD)@minio:9000` (credentials stay out of process args) and retries come from kubelet restarting a failed init container with backoff. If MinIO is down at apply time the Loki pod waits in Init and starts once MinIO answers.
- **Retention:** compactor with `retention_enabled: true`, `delete_request_store: s3`, `retention_delete_delay: 10m`, `compaction_interval: 10m`, and `limits_config.retention_period: 24h`, the same as Prometheus. Real bound: data older than 24h is marked, then deleted after the delay, so stored logs are about 24h plus a short tail. The MinIO PV is 5Gi and shared with `media` uploads. There is no write-side cap; a very noisy service could grow the bucket within the 24h window (accepted for a local cluster; watch `mc du`).
- **Alloy** (`grafana/alloy:v1.10.0`): DaemonSet with its own ServiceAccount `alloy`, args `run /etc/alloy/config.alloy --server.http.listen-addr=0.0.0.0:12345`, readiness probe `/-/ready` on 12345, env `NODE_NAME` from `spec.nodeName`. Config from a ConfigMap generated by kustomize from `config.alloy`. RBAC is a namespaced `Role` + `RoleBinding` in `raas` (discovery is limited to `raas`): `get/list/watch` on `pods`, `get` on `pods/log`. No ClusterRole. The config: `discovery.kubernetes` role `pod`, `namespaces { names = ["raas"] }`, `selectors { role = "pod" field = "spec.nodeName=" + sys.env("NODE_NAME") }`; `discovery.relabel` sets `namespace`, `pod`, `container`, `app` (from pod label `app`), drops targets whose `app` is `loki` or `alloy` (no log-about-logs feedback loop), and keeps a single target per container (pods with several declared ports, such as MinIO, would otherwise be tailed twice); `loki.source.kubernetes` tails through the Kubernetes API; `loki.write` pushes to `http://loki:3100/loki/api/v1/push`. No hostPath mounts. Alloy keeps no positions file across restarts, so a restart may duplicate or skip a few lines (accepted). Fallback to `loki.source.file` on `/var/log/pods` (hostPath, the one allowed deviation) only if, two minutes after deploy, Alloy logs show tail/403 errors or Loki has no `raas` lines; record it in Further Notes.
- **Labels:** low cardinality only: `namespace`, `pod`, `container`, `app`. Values of `app` are the pod labels as they exist (`listing-service`, `booking-service`, `payment-service`, `ui-service`, `gateway`, `kafka`, `minio`, ...). Log lines are shipped raw; no JSON or level parsing.
- **Scope:** namespace `raas` only. `kube-system` and other namespaces are excluded. Loki and Alloy pods are excluded too (see Alloy).
- **Grafana (edits in `k8s/infra/monitoring/`):** add a Loki data source (`uid: loki`, `url: http://loki:3100`) to `grafana-datasources.yaml`; add `dashboards/logs.json` to the `grafana-dashboards` ConfigMap generator in `kustomization.yaml`. Prometheus stays the default data source. Apply order of the two folders does not matter; Grafana only shows the data source as failing until Loki is up.
- **Logs dashboard:** variables `app` and `pod` (multi, include-all, from Loki label values); panels: log volume by app (`sum by (app) (count_over_time(...))`), error-line rate (`|~ "(?i)error"`), and a live log stream filtered by the variables.
- **No ingress, no NodePort.** Reach Loki or Grafana with `kubectl -n raas port-forward`.
- **Resources:** limits only (Loki 512Mi, Alloy 256Mi), like the monitoring stack.

## Testing Decisions

No application code changes, so no unit tests. The checks below are the tests.

Levels:

- **Manifests:** `kubectl kustomize k8s/infra/logging` and `k8s/infra/monitoring` render cleanly; `kubectl apply --dry-run=server -k` passes for both.
- **Deployment (local cluster):**
  - Loki and Alloy pods Ready; Alloy runs on every node (one node locally).
  - Loki `/ready` returns `ready`; the init container created bucket `raas-loki`.
  - Loki pod stays Running for 2 minutes with no restarts and `/ready` returns `ready`; Alloy logs show no 403 or tail errors.
  - Loki API `label/app/values` lists the real `app` values: all `*-service` apps, `gateway`, `kafka`, `minio`, `postgres`, `redis`, `mongodb`, the exporters, `prometheus`, `grafana`; it does not list `loki` or `alloy`.
  - A query for `minio` returns each line once (no double tailing).
  - A query for one service returns recent lines, and a line emitted after deploy (a request to a service) shows up; poll up to 60s.
  - Chunks in MinIO: within about 10 minutes (`max_chunk_age: 5m`), `mc ls -r` on bucket `raas-loki` shows chunk objects. `mc` runs in an ephemeral pod (`kubectl run --rm -it` with the pinned minio-client image and the same `MC_HOST_minio` env). Index files appear later (tsdb upload lag) and are not asserted.
  - Persistence across service restart: delete a service pod, its old logs are still queryable under the old `pod` label.
  - Retention config loaded: Loki `/config` shows `retention_period: 24h` and `retention_enabled: true` (data older than 24h cannot be tested in one session).
  - Grafana API lists the Loki data source and its health check passes (retry for up to 30s after Loki starts); the Logs dashboard is listed.
- **Manual (human):** open the Logs dashboard, pick an app, confirm the three panels show data and look right.

The local cluster must be running for the deployment and manual levels. If it is not, those levels are reported as not verified.

## Out of Scope

- Log parsing (JSON, level extraction), structured metadata, log-based alerts, Alertmanager.
- Metrics and traces through Alloy (later idea in the proposal).
- Collecting logs outside namespace `raas`.
- Persistent WAL, Loki scaling modes (read/write/backend split), multi-tenancy, auth, ingress, TLS.
- Per-service app changes (log format stays as is).
- CI changes (upstream public images; no service code touched).

## Further Notes

- The `grilling` step was run: all eight questions (bucket init, local state, retention, scope, Alloy method, labels, layout, dashboard panels) were accepted as recommended.
- Rollback: `kubectl delete -k k8s/infra/logging`; revert the two Grafana file edits and re-apply `k8s/infra/monitoring`. The bucket `raas-loki` stays in MinIO until removed with `mc rb --force`.
- Adversarial review handled:
  - Accepted: `mc` image is Chainguard `minio-client`, distroless, so exec-form command, auth through `MC_HOST_minio` env, retry by init-container restart; full monolithic Loki keys and S3 fields listed; compactor needs `delete_request_store`, `working_directory`, short `retention_delete_delay`; env keys are `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`; real `app` label values; single target per container (MinIO has two ports); `NODE_NAME` selector; namespaced Role instead of ClusterRole; probes and listen address; pinned tags; per-entry kustomize namespace; Loki/Alloy excluded from collection; restart caveats documented; chunk-flush test uses `max_chunk_age: 5m` and an ephemeral `mc` pod; fallback has a trigger.
  - Rejected: ingestion rate limits and a size cap (scope creep for a local cluster; documented as known limit); dashboard as Explore-only (the issue asks for log panels); `app` fallback for pods without the label (all `raas` pods have it).
- Code review handled:
  - Accepted: the `loki`/`alloy` drop rule also matches the pod name, so a pod without the `app` label cannot start a log-about-logs loop. Redeployed; 24 streams opened, none for loki or alloy.
  - Rejected: explicit per-port dedupe rule. Alloy opens one stream per container, not per port; verified, MinIO has exactly one `opened log stream`. The spec text "keeps a single target per container" is satisfied by Alloy itself, no relabel rule needed.
  - Rejected: memory requests and liveness probes (spec decision: limits only, local cluster). Rejected: URL-encoding the MinIO password for `MC_HOST_minio` (dev credentials, no reserved characters). Accepted as known limits: tiny chunks from `max_chunk_age: 5m` (chosen so the MinIO check is testable), substring `error` match in the dashboard panel.
  - Seen after an Alloy restart: Loki answers 400 "entry too far behind" for old lines Alloy re-reads (no positions file). Expected per the restart caveat above; Loki drops them.
